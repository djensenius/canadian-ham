## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Why: the task-12.3 final review found web edge cases: (1) close() waits exactly the 5 ms ramp by wall clock before context.close(), but browsers render whole device buffers, so leaving the page mid-tone can still click; (2) the stop fade is anchored at context.currentTime, which can lag (Firefox reduces timer precision), shortening or skipping the ramp; (3) out-of-range number input reverts silently.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 close() waits at least ramp + baseLatency + outputLatency + a margin (about 100 ms total), with a test
- [x] #2 The stop fade is robust to a stale currentTime (e.g. setTargetAtTime from currentTime, or a ramp started slightly ahead), with a test
- [x] #3 Out-of-range Morse number input explains the revert or clamps, announced politely; web tests and axe pass
<!-- AC:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Tighten WebMorsePlayer stop/close timing so fades tolerate stale currentTime and close waits for audio device latency plus margin.
2. Cover stop/close behavior with fake-timer tests.
3. Improve Morse number input invalid-draft feedback with a polite announcement and web/axe coverage.
<!-- SECTION:PLAN:END -->
